# bitcoin-full-history-sync

Keeps a fork with a **rewritten-base history** up to date with its **upstream**,
putting new commits **on top** without breaking the base.

Built for a repository that reconstructs Bitcoin's early history (the November
2008 *preview*, v0.1.0/v0.1.3 and the SourceForge SVN era with **real author
identities** instead of `user@<UUID>`) and links it to all of `bitcoin/bitcoin`
up to today. But the script is generic: it works for any fork whose old era has
different SHAs than the upstream.

## The problem

If you rewrite the base of the history (the old commits' SHAs change), your
`master` **shares no SHAs** with the upstream. Then:

- `git pull` / `merge` doesn't apply (histories with no common ancestor).
- `git rebase` of the new commits **re-merges** the upstream's merge commits and
  produces **conflicts**.
- `git cherry-pick` **flattens** merges (loses PR commits and topology).

## The solution

Deterministic re-splice with **`git replace` (graft) + `git-filter-repo`**:
it does not merge anything, it only rewrites the *parent* pointers of the old era
toward the rewritten commits. As a result:

- ✅ **0 conflicts** (no content merge).
- ✅ preserves **author, committer and the EXACT merge topology** of upstream.
- ✅ **deterministic**: already-published SHAs don't change → the push is a
  *fast-forward* (only the new commits are added).

## Requirements

- `git`, `bash`, `flock`, and [`git-filter-repo`](https://github.com/newren/git-filter-repo)
  (`pip install --user git-filter-repo`).
- The **base repo** (`PUB`) with the real-id base on a branch (`BASE_REF`, e.g. `svn`)
  and the `origin` remote pointing to your fork. **This is the only thing that
  must already exist.**

The two derived inputs are **bootstrapped automatically** on the first run (and can
also be built by hand):

- The **pristine mirror** (`MIRROR`): if missing, it is created with
  `git clone --mirror "$UPSTREAM" "$MIRROR"` (default upstream `bitcoin/bitcoin`).
- The **mapping file** (`MAP`): if missing, it is generated by `gen-splice-map.sh`
  — for each commit of the upstream's old era, its real-id equivalent in `BASE_REF`,
  one `RAW_SHA REALID_SHA` pair per line.

### `gen-splice-map.sh`

The mapping is **not** a plain tree match. It keys on
`author-ts | committer-ts | tree` (`%at|%ct|%T`): the real-id rewrite preserved
timestamps, message and tree and only changed the author identity, so this key is
unique in both histories. A pure tree match is ambiguous — a real revert that
restores an identical tree (e.g. *"revert revision 56"*) would collapse. It also
scans **all** upstream commits (`rev-list --all`), not only the linear ancestors of
the link point, so old-era side branches that merge in later are mapped too;
otherwise they keep their original SHAs and break determinism. Run it standalone to
(re)build the map:

```sh
./gen-splice-map.sh
```

## Usage

```sh
./bitcoin-full-history-sync.sh
```

Everything is configurable via environment (defaults under `$HOME`, no absolute
paths — user-agnostic):

| Variable   | Default                                  | What it is                               |
|------------|------------------------------------------|------------------------------------------|
| `MIRROR`   | `$HOME/git/bitcoin-mirror`               | `--mirror` clone of the upstream (auto)  |
| `UPSTREAM` | `https://github.com/bitcoin/bitcoin`     | URL to mirror-clone if `MIRROR` is absent|
| `PUB`      | `$HOME/git/bitcoin-full-history`      | repo with the real-id base (`BASE_REF`)  |
| `MAP`      | `$HOME/git/.bitcoin-splice-map.txt`      | `RAW_SHA REALID_SHA` mapping             |
| `BASE_REF` | `svn`                                    | base branch in `PUB` (up to the link)    |
| `BRANCH`   | `master`                                 | branch to level/publish                  |
| `ORIGIN`   | `git -C "$PUB" remote get-url origin`    | push URL of the fork                     |

### cron

```cron
0 */6 * * * /path/to/bitcoin-full-history-sync.sh
```

> The push in cron needs an SSH key **without a passphrase** (the script uses
> `GIT_SSH_COMMAND="ssh -o BatchMode=yes"`).

### GitHub Actions (weekly)

The workflow at [`.github/workflows/full-history-sync.yml`](.github/workflows/full-history-sync.yml)
runs **from this repo** and pushes the leveled `master` to the target fork
(`bitcoin-full-history`). Running it from the scripts repo, rather than from the
fork, keeps things clean:

- The schedule fires from this repo's default branch (just scripts, never rebuilt),
  so there is no clash with the deterministic `master` rebake.
- The **target repo can keep Actions disabled** — it only receives a push, so its
  heavy upstream `ci.yml` never runs.

Setup:

- Create a fine-grained **PAT** scoped to `bitcoin-full-history` with
  *Contents: Read and write*, and add it here as the secret `SYNC_TOKEN`. The
  built-in `GITHUB_TOKEN` can only write to *this* repo, so a cross-repo push needs
  the PAT.
- The mirror (~2.5 GB) is cached via `actions/cache`; only deltas are fetched on
  later runs. The `MAP` is regenerated each run (deterministic).
- A PAT push *does* trigger the target's workflows (unlike `GITHUB_TOKEN`), so keep
  Actions disabled in the target — or accept that its `ci.yml` will run.

**Determinism.** The bake is reproducible because filter-repo runs with
`--preserve-commit-hashes`: commit **messages** are kept byte-identical to
upstream, so the result is a pure function of *(DAG + MAP)*. Without that flag,
filter-repo rewrites hash references inside messages in a single streaming pass,
and whether a reference resolves depends on the order `git fast-export` emits
unrelated commits — an order that is unspecified and shifts both **across git
versions** and **as the repository grows**. One flipped reference changes a
published commit's bytes and cascades, turning the next push into a
non-fast-forward (this broke the weekly sync on 2026-08-16). As a safety net the
script also refuses to push unless the published tip is an **ancestor** of the
bake, so a divergence fails loudly instead of silently becoming a force-push.

The job still runs inside a pinned `ubuntu:24.04` container with
`git-filter-repo==2.47.0` — no longer as the guarantee of reproducibility, but as
cheap insurance against filter-repo's other version-dependent behaviour. Current
baseline: **`843d5adf9de8`**. The full byte-level analysis is in
[`NOTES.md`](NOTES.md).

## Notes

- Only `BRANCH` (`master`) is synced. The base branches/tags (e.g. `svn`,
  `svn-full`) stay frozen.
- Idempotent: if there's nothing new upstream, it does not push.
